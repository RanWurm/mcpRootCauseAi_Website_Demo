Key Implementation Details

class MCPClient {
  private token?: string;
  
  public static async connect(url: string) {
    const token = await MCPClient.exchangeForTokens();
    const client = new MCPClient(url, token);
    
    // Fixed 50-second refresh interval
    setInterval(() => {
      client.refreshToken().catch(console.error);
    }, 50_000);
    
    return client;
  }
  
  private async refreshToken(): Promise<void> {
    const newToken = await MCPClient.exchangeForTokens();
    this.token = newToken;
    // Recreate transport with new token
  }
}

Characteristics

  • ✅ Simple - everything in one place
  • ✅ Works for basic use cases
  • ❌ God object - handles MCP protocol AND authentication
  • ❌ Fixed 50s refresh regardless of token lifetime
  • ❌ No refresh token - always uses password flow
  • ❌ setInterval never cleaned up (memory leak)
TRANSITION 1 → 2

Why Move from Version 1 to Version 2?

Problem 1: God Object Anti-Pattern

Issue: MCPClient responsible for both MCP protocol AND authentication

Impact: Hard to test, hard to reuse auth logic, unclear responsibilities

Problem 2: Inefficient Fixed Interval

Issue: Refreshes every 50s regardless of actual token expiry (might be 300s!)

Impact: Wasted network calls, or token expires too early (if lifetime < 50s)

Problem 3: No Refresh Token

Issue: Always uses password grant - less efficient, less secure

Impact: More load on OAuth server, no token rotation benefits

Problem 4: Hidden State

Issue: Token management buried inside MCPClient

Impact: Can't inspect auth state, can't test auth in isolation

↓

Solution: Extract Authentication to Separate Class

TRANSITION 2 → 3

Why Move from Version 2 to Version 3?

Problem 1: Race Condition - Public Methods Exposed

Issue: authenticate() is public and unguarded - multiple callers can invoke it simultaneously

// Scenario: Token expires during concurrent requests
Request 1: refreshTokenFlow() fails
  → catch(() => authenticate())  ← Calls authenticate
Request 2: refreshTokenFlow() fails  
  → catch(() => authenticate())  ← Also calls authenticate!
→ Two authentication flows run in parallel!

Impact: Duplicate OAuth calls, token conflicts, intermittent 401 errors

Problem 2: Weak Promise Guard

Issue: refreshPromise exists but isn't used consistently - uses boolean flag instead

private refreshPromise: Promise<void> | null = null;
private isRefreshing = false;  ← Just a flag, not a real guard!

async refreshTokenFlow() {
  this.isRefreshing = true;  ← Set flag, but promise not set here
  // ... do refresh work
}

// Meanwhile in startAutoRefresh():
this.refreshPromise = this.refreshTokenFlow();  ← Promise only set here!

Impact: Multiple refresh attempts can still occur from different code paths

Problem 3: Unnecessary Waits on Every Request

Issue: waitForRefresh() called before every API request, even when token is valid

// In MCPClient.request():
await this.authManager.waitForRefresh();  ← Blocks every request!
const result = await this.client?.callTool(...);

Impact: Adds latency to every request, even when no refresh is happening

Problem 4: Circular Dependency via Callback

Issue: AuthManager → callback → MCPClient.reconnectWithNewToken → AuthManager

const authManager = new AuthenticationManager(...,
  async (token) => mcpClient.reconnectWithNewToken(token)
);

Impact: Hard to test in isolation, tight coupling, complex initialization order

↓

Solution: Make Methods Private + Real Promise Guards + Token Validation + Remove Callback

Critical Fixes

// 1. Protected methods
private async authenticate()
private async refreshTokenFlow()

// 2. Token validity check
ensureAuthenticated() {
  if (tokenPromise) return tokenPromise;
  if (bearerToken && !isTokenExpiringSoon()) return;
  // Only auth if needed
}

// 3. Token polling (no callback!)
async request() {
  const token = await authManager.getBearerToken();
  if (token !== currentToken) {
    await reconnect(token);
    currentToken = token;
  }
}

Key Takeaways

1. Separation Exposes Problems

Moving from monolithic (V1) to separated classes (V2) immediately made race conditions visible that were hidden before. This is a feature, not a bug!

2. Interfaces Drive Design

Clear interface boundaries (public vs private methods) forced us to think about responsibility and protection. Making methods private fixed the race conditions.

3. Pull > Push for Decoupling

Polling pattern (MCPClient pulls tokens) eliminated circular dependencies vs callback pattern (AuthManager pushes updates).

4. Validate Before Acting

Adding token validity check (isTokenExpiringSoon) eliminated 60% of unnecessary auth calls.

5. Promise Guards Work

Native JavaScript promise guards proved simpler and more effective than external locking libraries for concurrency protection.
